How Camerata works

Camerata is the engine I built for this work. It reads every file in your repository against written rules for security and architecture, and every judgment call comes to me.

Two passes, then a person

  • A mechanical pass · for what a rule can decide exactly: leaked keys, unsafe database access, settings that leave a door open.
  • A reasoning pass · for the architecture: a write with no check on who is allowed, a service that goes around the data layer, the same logic written twice.
  • One person · who reviews every pattern, every critical finding and every uncertain call before you see them.

The engine proposes. I decide. The report says how many candidates I threw out.

What every finding carries

  • The standard it breaks · with a link, so your next engineer can check my work, not take my word.
  • The hours it takes to fix · so the report answers "fix or rebuild" in numbers.
  • How certain it is · where I am not certain, the report says so.

Why written rules

I learned this on my own projects. An agent kept putting database calls in the service layer, despite the separation I had set up in example endpoints. The examples were not enough. So I wrote a hard rule and had a machine enforce it: database calls live only in the repository layer. It hasn't made that mistake since.

Examples are not enforcement. Rules are.

What you can check yourself

  • 437 written rules, 410 of them traceable to a published standard.
  • Source-available on GitHub, so you can read it before you hire me.
  • Camerata is checked against its own rules on every change.
