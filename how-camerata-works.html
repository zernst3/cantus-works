How Camerata works

Camerata is the engine I built for this work. The engine supplies the structure: it lists every source file, makes sure each one is read and keeps the record. AI models supply narrow judgment, each answering one question, using the smallest model that answers it well. Every call that matters comes to me.

One engine, narrow AI jobs, then a person

  • Automated checks · for what a rule can decide exactly: leaked keys, unsafe database access, settings that leave a door open and every block of code that was copied.
  • Narrow AI jobs · the strongest model reads every source file against the rules for your stack, then checks its own work rule by rule. Smaller, faster models each answer one closed question: is this copy the same decision, what is the fix, is this the same problem written twice.
  • One person · who reviews every critical problem and every call the engine isn't sure of before you see them.

The engine proposes. I decide. The report says how many candidates I threw out. Coverage never depends on a model's attention: the record of what was read is the coverage list in your report.

What every problem carries

  • The standard it breaks · with a link, so your next engineer can check my work, not take my word.
  • The hours it takes to fix · so you can budget the fixes.
  • How certain it is · where I am not certain, the report says so.

Why written rules

I learned this on my own projects. An agent kept putting database calls in the service layer, despite the separation I had set up in example endpoints. The examples were not enough. So I wrote a hard rule and had a machine enforce it: database calls live only in the repository layer. It hasn't made that mistake since.

Examples are not enforcement. Rules are.

What you can check yourself

  • Over 400 written rules, nearly all traceable to a published standard.
  • Source-available on GitHub, so you can read it before you hire me.
  • Camerata is checked against its own rules on every change.
