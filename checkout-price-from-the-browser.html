The checkout bug a pattern scanner won't flag

Your checkout works. Customers pay, the money arrives, nothing crashes. And any signed-in user can still pay whatever price they like.

What it looks like

This one is from the sample report, on a small demo app built with Next.js, Supabase and Stripe. The checkout route reads the amount to charge from the request the browser sends:

const { bookingId, amountCents } = await req.json();

Then it creates the Stripe payment for amountCents, and works out the platform's fee from the same number. The booking's real price is in the database, but the route never looks it up. Anyone who opens their browser's developer tools can change the number before it's sent, and the server charges what it's told.

The route does check that the booking belongs to the person paying. So a user can't pay for someone else's booking, but they can pay one cent for their own, and the platform's fee drops with it.

Why it's so common now

AI tools build features from the front end back. The form already shows the price, so the quickest way to pass it to the payment step is to send it along. It works in every test, because nobody tests with a tampered request.

Why pattern scanners miss it

Tools like Semgrep and Dependabot match known patterns and known vulnerable packages, and they're worth running. But there's nothing wrong with the line above as code. The problem is a decision: which number should the server trust? Answering that means knowing the amount is a price, that a price belongs to the server and that the booking query already has it. That's a business-logic flaw, and business-logic flaws need someone to read the code with its purpose in mind.

How to fix it

  • Take the price from your own records · look up the booking on the server and charge its stored price. The browser sends only what's being bought, never what it costs.
  • Compute the fee from the same server-side price · never from anything the browser sent.
  • If the browser does send an amount · use it only to compare against the server's price, and stop on a mismatch.

In the sample report this is rated critical, with an estimate of 2 to 4 hours to fix. Every finding in a report comes the same way: the place in the code, the standard it breaks, the fix and the hours.
