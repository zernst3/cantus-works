What a Cantus Works inspection checks

Every inspection reads your whole repository against the rules that apply to your stack, drawn from a library of over 400. Nearly all of them cite the published standard they come from: the platform's own documentation, its security advisor or an established reference such as OWASP.

Deepest today on Next.js and Supabase. Rules also cover Firebase (including Flutter apps), Python, C#, Go, Java, Ruby and Rust. The quote step tells you how well your stack is covered before you commit. The sample report is a real run on a small demo app; its reviewer decisions are illustrative until a fully reviewed sample replaces it. Camerata has not yet inspected a large real-world codebase.

Security

  • Keys and secrets · credentials committed to the repository, written into code, printed in build logs or exposed to the browser.
  • Data access · who can read and change which records, checked on the server, not just hidden in the interface.
  • Sign-in and sessions · sessions trusted without being verified, tokens that live too long, weak password and sign-in settings.
  • Databases and migrations · changes that can lose data, writes that can half-finish, money stored as approximate numbers, functions with more power than they need.
  • APIs and server code · input that isn't validated, errors that leak internal details, failures swallowed silently, requests that can't be safely retried.
  • Payments · webhooks that aren't verified or can be replayed, order status out of sync with the payment provider, refunds anyone can trigger, card data stored where it shouldn't be.
  • Front-end code · data sent to the browser that should stay on the server, misused React hooks, lists that re-render incorrectly.
  • Build and deployment · secrets printed in CI, pipelines with more permission than they need, production changes without a review gate.
  • File uploads and storage · private files in public locations, file names taken straight from the user.

Consistency and quality

Beyond security, I check the caliber of your code: whether it does the same thing in one consistent way, whether it follows sound architecture, whether the same logic is written more than once and whether your tests actually test anything. The report also lists the good practices your code already follows consistently, so you know what to keep.

A mechanical check

No hardcoded credentials

The question

Where do credentials (API keys, tokens, passwords) live?

Sources

  • CWE-798: Use of Hard-coded Credentials
  • OWASP Secrets Management Cheat Sheet

What it requires

Credential values never appear in committed source or config; they come from environment variables or a secrets manager.

Rejected alternative, and why

Allow hardcoded credentials in internal-only tools. Rejected: who can read a repository changes over time, and a credential hardcoded "for now" outlives the assumption.

The fix it recommends

Remove the value, load it from the environment or a secrets manager and rotate it, since a committed secret must be treated as disclosed.

The rule file, exactly as Camerata reads it
id = "SEC-NO-HARDCODED-SECRETS-1"
version = 4
title = "Credential literals (API keys, tokens, passwords) are never hardcoded in source; they live in environment variables or a secrets manager"
domain = "universal"
layer = "universal"
enforcement = "mechanical"
kind = "defect"
inspectable = true
cwe = ["CWE-798"]
default = true
verification = "grounded"

[[sources]]
url = "https://cwe.mitre.org/data/definitions/798.html"
title = "CWE-798: Use of Hard-coded Credentials"

[[sources]]
url = "https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html"
title = "OWASP Secrets Management Cheat Sheet"

[decision]
question = "Where do provider-agnostic credential literals (a key/secret/token/password assigned to a named variable) live?"
default = "env-or-secrets-manager"
why = """
`SEC-NO-VENDOR-TOKEN-1` catches known vendor-specific token SHAPES (AWS AKIA, GitHub gh*_, Stripe
sk_live_, …). This rule catches the provider-agnostic case those fixed-prefix patterns miss: a
long opaque literal assigned to an identifier whose name itself carries key/secret/token/
password/credential vocabulary (e.g. a Finnhub or other third-party API key with no distinctive
prefix of its own). The gate matches on the NAME-then-VALUE pattern rather than a vendor prefix,
so it generalizes to any provider without a dedicated shape rule. Once matched, the same remedy
applies regardless of vendor: the literal does not belong in source, and having been committed,
it must be treated as already disclosed.
"""

[[option]]
id = "env-or-secrets-manager"
label = "Credential literals live in env vars or a secrets manager, never source"
directive = "A quoted literal of 24+ contiguous alphanumeric characters assigned near an identifier containing key/secret/token/password/credential vocabulary is never written into a source or config file committed to the repository. Tests that need a credential value use an environment variable, a secrets manager fetched at test startup or a clearly-fake placeholder that cannot be mistaken for the shape of a real key. The gate enforces this with a heuristic match (identifier vocabulary + a nearby long opaque literal); it is not an entropy/AST analysis, so it complements rather than replaces a dedicated secret-detection tool. Not a credential: a reference to one (an environment variable name, a secret manager or secret object name, a Terraform expression), a value encrypted for committing (a sealed secret), a module path, a label or cache key and the id of a domain object that happens to be called token or key. A value in a test file is reported as low and needs review."
remediation = """
Remove the hardcoded credential literal from the source or config file, and load it from an environment variable or secrets manager instead. Rotate the exposed value, since it was committed to version control and must be treated as disclosed. Verify by searching the codebase for the literal value and confirming it no longer appears, while the integration still authenticates using the externally-loaded value.
"""
effort = "low"
finding_headline = "Your `<path>` file has a credential value hardcoded directly in the source."
finding_detail = """
A secret written directly into source code ships to everyone who can read this repository (including its full git history) rather than staying somewhere access can be revoked without a code change. The value in `<path>` is <gitignore-status> and is <history-status>. Move it to an environment variable or secrets manager, and rotate the exposed credential.
"""
why = "A hardcoded credential is disclosed the moment the commit is pushed, whether or not the repository is public today: a repository's visibility can change, forks persist independently and CI logs/artifacts routinely echo file contents. Name-vocabulary + opaque-literal matching catches providers with no fixed token shape of their own, closing the gap `SEC-NO-VENDOR-TOKEN-1`'s prefix-anchored patterns leave open."

[[option]]
id = "allow-hardcoded-for-internal-tools"
violates = true
label = "Allow hardcoded credentials in internal-only tooling"
directive = "credential literals may be hardcoded in scripts or tools that are never deployed externally, on the assumption that only trusted engineers can read the repository"
why = "Rejected: repository access scope changes over time (new hires, contractors, an accidental visibility flip, a fork), and a credential hardcoded 'for now' outlives the assumption that justified it. The environment-variable/secrets-manager pattern costs one extra line at call time and removes the assumption entirely."

A rule with rejected alternatives

Retries never double-charge

The question

When a client retries a write that charges a card, sends an email or starts a job, how does the API keep it from happening twice?

Sources

  • IETF draft: the Idempotency-Key HTTP header
  • Stripe: Idempotent Requests

What it requires

Every write with an external side effect accepts an idempotency key; a retry with the same key returns the stored result instead of running the operation again.

Rejected alternative, and why

No idempotency contract, or no server-side deduplication at all. Rejected: networks time out, the client can't tell whether the first request landed and without a key every retry risks a double charge or a duplicate email.

The fix it recommends

Require the key on the endpoint, store the response by key and verify by sending the same request twice.

The rule file, exactly as Camerata reads it
id = "ARCH-IDEMPOTENCY-KEYS-1"
version = 3
title = "Non-GET writes that trigger external side effects require an idempotency key"
domain = "api-layer"
layer = "universal"
enforcement = "structured"
kind = "default_with_exceptions"
inspectable = true
default = true
verification = "grounded"

[[sources]]
url = "https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/"
title = "IETF: The Idempotency-Key HTTP Header Field (draft-ietf-httpapi-idempotency-key-header)"

[[sources]]
url = "https://docs.stripe.com/api/idempotent_requests"
title = "Stripe: Idempotent Requests"

[decision]
question = "When a client retries a write that charges a card, sends an email or enqueues a job, how does the API keep the side effect from happening twice?"
default = "non-get-writes-that-trigger-external-side-effects-require-an-idempotency-key"
why = "Network retries are inevitable. Without idempotency keys, a client cannot safely retry after a timeout because the original may have succeeded silently. With keys, the client retries freely until it gets a definitive response, and the server never double-executes. Allowing retries without keys means the client risks double-charging or sending duplicates on every timeout, because the network cannot tell the client whether the original request reached the server. Deduplicating via natural keys works only when natural keys exist, are stable and uniquely identify the intended effect, and many real operations have no such key (a payment intent, an outbound email, an external job enqueue). Making the client responsible for not retrying pushes correctness onto every consumer; one careless caller produces duplicates and the server has no way to defend against it."

[[option]]
id = "non-get-writes-that-trigger-external-side-effects-require-an-idempotency-key"
label = "Non-GET writes that trigger external side effects require an idempotency key"
directive = "POST, PUT, PATCH and DELETE endpoints that produce external side effects (charge a card, send an email, enqueue a downstream job, write to a message queue) require an Idempotency-Key header on each request. The server stores the response keyed by that key; a retry with the same key returns the stored response instead of running the operation again. Reads and writes that are naturally idempotent at the storage layer may omit this. The key-retention window is bounded (commonly 24 hours) and documented per endpoint. A violation of THIS rule is a side-effecting write ENDPOINT that has no idempotency-key mechanism in use at all, not the mere presence of an idempotency-key helper/utility function in the codebase and not a helper that is defined but not (yet) called from any endpoint. An unused helper is a dead-code/hygiene concern for a DIFFERENT rule, never evidence of an idempotency defect under this one; do not report it here."
remediation = """
Require an Idempotency-Key header on the endpoint and store the response keyed by that value so a retried request with the same key returns the stored response instead of re-running the side effect. Apply this to every POST/PUT/PATCH/DELETE endpoint that charges a card, sends an email, enqueues a job or otherwise triggers an external effect. Verify by sending the same request twice with the same Idempotency-Key and confirming the side effect (charge, email, job) only happens once.
"""
why = "Network retries are inevitable."

[[option]]
id = "the-api-accepts-retries-without-any-idempotency"
violates = true
label = "No idempotency contract"
directive = "the API accepts retries without any idempotency-key contract; the client is expected to detect prior success out of band before retrying"
why = "No idempotency contract means the client risks double-charging or sending duplicates on every timeout, because the network cannot tell the client whether the original request reached the server."

[[option]]
id = "the-api-deduplicates-requests-by-inspecting-natu"
label = "Deduplicate by natural keys"
directive = "the API deduplicates requests by inspecting natural keys in the payload (such as an email address or invoice number) rather than by requiring an explicit Idempotency-Key header"
why = "Natural-key deduplication works only when natural keys exist, are stable and uniquely identify the intended effect; many real operations have no such key (a payment intent, an outbound email, an external job enqueue)."

[[option]]
id = "the-api-does-no-server-side-deduplication-at-all"
violates = true
label = "No deduplication"
directive = "the API does no server-side deduplication at all; each consumer is responsible for not retrying after a timeout, and the server treats every request as new"
why = "Pushing correctness onto every consumer means one careless caller produces duplicates and the server has no way to defend against it."

A consistency rule

One logger, used everywhere

The question

Once a structured logger is in use, does every log call go through it?

Sources

  • OWASP Logging Cheat Sheet
  • OWASP Logging Vocabulary Cheat Sheet

What it requires

In a repository that has already adopted a structured logger, every operational log line goes through it. It only fires on inconsistency; it never says a repository must adopt one.

Rejected alternative, and why

Allow mixed logging styles. Rejected: a log search built around the structured format silently misses every line that bypasses it.

The fix it recommends

Swap each bare print or console call for the same message through the existing logger, at the same level.

The rule file, exactly as Camerata reads it
id = "ARCH-OBSERVABILITY-LOG-CONSISTENCY-1"
version = 3
title = "Once a repo has adopted a structured logger, every log call site goes through it; bare print/console-style calls do not sit alongside it"
domain = "universal"
layer = "universal"
enforcement = "architectural"
kind = "defect"
inspectable = true
# Severity ceiling: findings from this rule are capped at Low, whatever severity the model proposes.
max_severity = "low"
default = true
verification = "grounded"
qualifies = "This is an INCONSISTENCY check, not a 'you must adopt structured logging' stance; it only fires once a repo has ALREADY adopted a structured logger (slog/zap/winston/pino/slf4j/serilog/tracing, or an equivalent project-specific wrapper) and some OTHER call site in the same repo still uses a bare print/console-style call alongside it. For Go and Java specifically, the 'always use structured logging' stance itself is already covered by GO-LOGGING-STRUCTURED-1 and JAVA-LOGGING-STRUCTURED-1 (both full-severity, per-language prose rules), so this rule does not re-litigate that stance for those two languages; it exists for (a) every OTHER stack (Python, JS/TS, Rust, C#, Ruby) where no per-language stance rule already covers the question, and (b) the cross-stack/multi-language case where the inconsistency is between files or layers rather than within a single language's own convention. Camerata has no deterministic check for this rule; the model-assisted review finds it, and its findings are capped at severity Low. A bare print/console-style call that is the CLI tool's actual stdout product, or that appears in a test or script file where print output IS the point, is out of scope and not flagged."

[[sources]]
url = "https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html"
title = "OWASP Logging Cheat Sheet, 'Use a standard logging library/format': consistent use of one logging approach across an application, rather than ad hoc print statements alongside it"

[[sources]]
url = "https://cheatsheetseries.owasp.org/cheatsheets/Logging_Vocabulary_Cheat_Sheet.html"
title = "OWASP Logging Vocabulary Cheat Sheet: a shared log event vocabulary/format presupposes every event is emitted through the same logging mechanism"

[decision]
question = "Once a structured logger is already in use somewhere in the repo, does every log-shaped call site go through it, or do bare print/console.log/puts/fmt.Println-style calls still sit alongside it?"
default = "one-logger-for-the-whole-repo"
why = """
A structured logger's entire value (machine-parseable fields, consistent levels, a single place to
configure output format/destination/filtering) is undermined the moment some call sites bypass it: a
log aggregator built to parse the structured logger's JSON output silently drops (or mis-parses) a bare
`print`/`console.log` line sitting in the same log stream, and a developer searching logs by field
learns nothing from the call sites that never emitted one. This is specifically an INTERNAL CONSISTENCY
defect, not a stance about whether structured logging is good (that question belongs to the per-language
rules, e.g. GO-LOGGING-STRUCTURED-1): a repo that has already paid the cost of adopting slog/zap/pino/
slf4j and then leaves some fraction of its own call sites on bare print statements gets none of the
consistency benefit and all of the adoption cost. Scoped deliberately to REPOS THAT HAVE ALREADY
ADOPTED a structured logger somewhere; a repo with no structured logger anywhere is a different
question (the per-language stance rules), not this one.
"""

[[option]]
id = "one-logger-for-the-whole-repo"
label = "Every log call site in the repo goes through the same adopted structured logger; no bare print/console-style calls alongside it"
directive = "In a repository that has already adopted a structured logger (slog/zap/winston/pino/slf4j/serilog/tracing, or an equivalent project-specific wrapper) at one or more call sites, every log-shaped call site goes through that logger; a bare print/console.log/puts/fmt.Println-style call emitting an operational event, an error or a status update does not sit alongside it. Every such message therefore lands in the same structured format and the same aggregated stream as the rest of the repo's logs, rather than a fraction of them bypassing the logger a log aggregator was built to parse. A call site that goes through the adopted logger is conforming regardless of its level or format."
remediation = """
Replace the ad hoc print/console-style call with a call through the repo's existing structured logger,
at the same log level and with the same message content, rather than introducing a second logging
mechanism. If no equivalent level/call exists yet in the adopted logger's usage elsewhere in the repo,
add one rather than falling back to a bare print. Verify by confirming the replaced call site's output
now appears in the same structured format (and, where applicable, the same aggregated log stream) as
every other log line in the repo.
"""
effort = "low"
why = "The fix is a like-for-like swap (the same message, the same level, through the already-adopted logger instead of a bare print call), so it carries none of the cost of adopting structured logging in the first place, only the cost of finishing an adoption the repo already started."

[[option]]
id = "allow-mixed-logging-styles"
violates = true
label = "Allow bare print/console-style calls to coexist with the repo's adopted structured logger"
directive = "Individual files or call sites may use a bare print/console.log/puts/fmt.Println-style call even in a repo that has otherwise adopted a structured logger elsewhere."
why = "Rejected: a log aggregator or a field-based search built around the structured logger's output format gets a silently incomplete picture the moment some call sites bypass it: the repo pays the full cost of adopting structured logging and still does not get a complete, uniformly-parseable log stream out of it."
